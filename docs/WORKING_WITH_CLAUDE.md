# Работа над проектом с Claude Code

Этот файл — для вас (владельца проекта), не для Claude. Он объясняет, как эффективно работать над проектом через Claude Code.

## Первый запуск

```bash
git clone https://github.com/ВАШ_USERNAME/vpn-blocked-apps-tracker.git
cd vpn-blocked-apps-tracker
claude
```

Claude Code автоматически прочитает `CLAUDE.md` в корне. Этого достаточно для общего понимания. Детальные правила в `.claude/rules/*.md` подгрузятся, когда Claude будет работать с соответствующими файлами.

## Хорошие первые промпты

Эти задачи уже описаны в `docs/ROADMAP.md`, можно просто сказать «возьми задачу P0-1 из roadmap», но если предпочтительнее явно — вот формулировки:

### Проверить парсеры
```
Прогони `python -m scraper.main` локально и покажи мне результаты по каждому
источнику. Где парсер вернул мало или много мусора, открой URL источника,
посмотри вёрстку и предложи, как улучшить парсер. Не правь код пока — сначала
покажи план.
```

### Зафиксировать парсеры тестами
```
Создай tests/fixtures/ и для каждого источника сохрани текущий HTML в
файл вида <source>_<today>.html. Потом напиши tests/test_sources.py
с по одному тесту на источник. Шаблон тестов — в .claude/rules/testing.md.
```

### Добавить приложение
```
Добавь "Магнит" (магазин) в aliases.yaml. Категория retail. Алиасы:
"магнит", "magnit", "magnit.ru".
```

### Добавить источник
```
Добавь источник Lenta.ru, URL: https://lenta.ru/news/2026/04/15/perestali-otkryvatsa/.
Сделай по шаблону существующих парсеров. Не забудь записать в sources.yaml.
```

## Что Claude Code должен делать сам, без напоминаний

Эти правила уже в `CLAUDE.md` и `.claude/rules/`:
- Не редактировать руками `README.md` корневой и `data/apps.json`.
- Перед коммитом — прогонять `pytest tests/ -v`.
- Новое приложение → правка `aliases.yaml`, не кода.
- Новый источник → отдельный файл в `scraper/sources/`, не правка `main.py`.

Если Claude нарушает эти правила — сначала проверь, видит ли он `CLAUDE.md`. Команда `/memory` внутри Claude Code покажет, что загружено.

## Workflow для типичной правки

1. **Опиши задачу.** Если она есть в `docs/ROADMAP.md` — сошлись на неё.
2. **Попроси план.** «Не правь код пока, покажи план изменений.»
3. **Согласуй план.** Скорректируй детали.
4. **Дай зелёный свет.** «Делай.»
5. **Перед коммитом**: «Прогони тесты и покажи diff.»
6. **Коммит** — можно поручить Claude или сделать самому. Если поручаешь Claude, формат: `<type>: <description>` (`feat:`, `fix:`, `chore:`, `docs:`).

## Чего избегать в промптах

- **«Перепиши всё на async»** — большие переделки без явной нужды. Проект маленький, синхронного кода достаточно.
- **«Добавь логирование везде»** — `main.py` уже логирует основное, парсеры намеренно тихие.
- **«Используй pandas»** — данных тут смешные объёмы, pandas-overkill.
- **«Сделай красиво»** без указания «как» — Claude может потратить полдня на рефакторинг ради рефакторинга.

## Если Claude ошибается

- **Игнорирует правило из `CLAUDE.md`** — переформулируй правило короче и положи в раздел «Hard rules».
- **Уходит в дебри** — `Esc` и попроси план перед действиями.
- **Уверенно делает не то** — попроси «найди в проекте, где это уже сделано, и скопируй паттерн оттуда».
- **Сломал тесты** — `git checkout .` и начинай заново с более узким промптом.

## Полезные команды в сессии

- `/memory` — показать загруженные правила и заметки.
- `/clear` — очистить контекст сессии (не путать с `/compact`, который пытается ужать историю).
- `#` в начале сообщения — попросить Claude запомнить что-то в auto memory (например, «# мой VPN — Hiddify» если это влияет на тестирование).

## Поддержка `CLAUDE.md` в актуальном состоянии

Раз в пару недель:
- Перечитай `CLAUDE.md` свежим взглядом — нет ли там устаревшего?
- Что-то стало очевидным после нескольких сессий — можно удалить.
- Что-то Claude часто делает не так — добавить в Hard rules.

Цель — держать файл коротким. Длинный CLAUDE.md съедает контекст и работает хуже короткого.
