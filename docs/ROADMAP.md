# Roadmap

Приоритизированный список задач. Сверху — самое важное. Каждая задача — самостоятельный кусок работы, который можно поручить Claude Code одной сессией.

## P0 — критично для запуска

### [ ] Проверить парсеры на реальных URL

Текущие парсеры используют дефолтный шаблон «все `<li>` короче 200 символов». Это сработает для большинства источников, но не для всех — у некоторых СМИ списки приложений могут быть оформлены через таблицы, абзацы или нестандартные структуры.

**Что сделать:**
1. Запустить `python -m scraper.main` локально (нужен интернет).
2. Посмотреть в лог: для каждого источника указано, сколько сырых элементов извлёк парсер и сколько матчей в `aliases.yaml`.
3. Если у источника матчей < 5 или сырых элементов > 200 — парсер нуждается в кастомизации.
4. Для проблемных источников: открыть URL в браузере, через DevTools найти селектор контейнера со списком приложений, переписать `parse()` в соответствующем файле под него. См. @.claude/rules/parsers.md.

**Definition of done:** все 4 источника возвращают ≥ 5 матчей при локальном прогоне.

### [ ] Создать HTML-фикстуры и тесты парсеров

После того как парсеры подтверждены на живых URL, зафиксировать их поведение тестами.

**Что сделать:**
1. Создать `tests/fixtures/`.
2. Для каждого источника: сохранить текущий HTML в `tests/fixtures/<source>_<date>.html`.
3. Написать тесты в `tests/test_sources.py` по шаблону из @.claude/rules/testing.md.
4. Цель: 4 теста (по одному на источник), проверяющих минимальный набор приложений (Ozon, Wildberries, VK как sanity check).

**Definition of done:** `pytest tests/ -v` показывает ≥ 19 passed (15 текущих + 4 новых).

## P1 — полезно в первый месяц

### [ ] Пополнить `aliases.yaml` по результатам первых прогонов

В словаре сейчас 24 приложения — это базовый набор из статей. После запуска снапшоты (`data/snapshots/`) покажут, какие сырые строки парсеры извлекают, но не матчат. Если среди немэтчей часто встречается одно и то же название — добавить в `aliases.yaml`.

**Что сделать:**
1. Прогнать скрипт хотя бы 3-4 дня (или несколько раз вручную через workflow_dispatch).
2. Открыть последний снапшот, посмотреть `run_results[<source>]` — это то, что _уже_ нормализовано.
3. Запустить временный скрипт, который покажет _сырые_ результаты без нормализации:
   ```python
   import requests
   from scraper.sources import hitech_mail
   html = requests.get("URL").text
   raw = hitech_mail.parse(html)
   print("\n".join(raw))
   ```
4. Сравнить с `aliases.yaml`, добавить недостающее.

**Definition of done:** ≥ 90% сырых строк парсера матчатся (если оставшиеся 10% — мусор типа "Подписаться" / "Читать дальше", это норма).

### [ ] Добавить уведомление о сбоях

Сейчас если workflow упал — об этом узнаешь только зайдя на вкладку Actions. Нужно push-уведомление.

**Варианты (выбрать один):**
- Telegram-бот: переменная `TELEGRAM_BOT_TOKEN` в secrets, `TELEGRAM_CHAT_ID` тоже, шаг в workflow `if: failure()` шлёт сообщение через `curl`.
- Discord webhook: ещё проще, один URL в secrets.
- Email через `dawidd6/action-send-mail@v3` — требует SMTP-настроек.

**Что сделать:**
1. Выбрать канал.
2. Добавить секреты в Settings → Secrets and variables → Actions.
3. Добавить шаг `Notify on failure` в `.github/workflows/update.yml` с `if: failure()`.

### [ ] CHANGELOG.md с автоматической дельтой

Раз в день в коммит-сообщении писать, что изменилось: «Добавлено: X, Y. Архивировано: Z.»

**Что сделать:**
1. Добавить в `scraper/main.py` логику дельты: сравнить `existing` и `updated`, посчитать новые / архивированные / переставшие подтверждаться.
2. Записать в `CHANGELOG.md` в формате:
   ```
   ## 2026-05-18
   - Добавлено: Магнит, Сбер Маркет
   - Архивировано: HeadHunter (последнее подтверждение 30 дней назад)
   ```
3. В `.github/workflows/update.yml` поменять коммит-сообщение, чтобы оно включало дельту.

## P2 — было бы здорово

### [ ] Веб-страница (GitHub Pages)

Простой `index.html` в корне или в `/docs`, который красиво показывает `apps.json`. Без бэкенда, всё через `fetch('data/apps.json')` + рендеринг на JS.

Стек: vanilla JS или Alpine.js. Без сборки, без npm — просто один HTML-файл.

Settings → Pages → деплоить из `main` branch, `/docs` folder.

### [ ] RSS-лента изменений

Генерировать `data/feed.xml` параллельно с README, чтобы можно было подписаться на изменения через RSS-ридер.

### [ ] Расширить набор источников

Кандидаты, которые я видел в исследовании, но не добавил в MVP:
- Lenta.ru (lenta.ru/news/2026/04/15/perestali-otkryvatsa/)
- Газета.Ru
- Android Insider (androidinsider.ru — у них исследование RKS Global)
- AppleInsider.ru

### [ ] Различать платформы (web / iOS / Android)

Сейчас все приложения в одной куче. Источники иногда уточняют, что блокировка работает только на Android или только в браузере. Добавить поле `platforms: ["web", "android", "ios"]` в `apps.json`. Потребует миграции схемы (см. @.claude/rules/data-format.md).

### [ ] Веб-форма для сообщений от пользователей

GitHub Issues с шаблоном «Я заметил, что приложение X блокирует меня с VPN» → автоматическая обработка через ещё один workflow → добавление в `aliases.yaml`. Сложно, но полезно — превращает проект в комьюнити-driven.
